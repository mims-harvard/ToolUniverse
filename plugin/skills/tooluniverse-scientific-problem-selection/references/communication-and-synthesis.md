# Communication and Synthesis: Turning the Conversation into a Decision

Use this module at the end of any entry point (pitch, troubleshoot, strategic question), or when the user asks "so what do I tell my PI / committee / collaborators?". It pulls the earlier modules into one short artifact and sets the order in which to run them when the user wants the whole framework.

## Running the whole framework in order

Only do this when the user explicitly wants a complete workup; for a narrow question use just the module that answers it.

1. **Sharpen** the idea (`idea-evaluation.md`): one-paragraph kernel, why it matters if it works.
2. **Ground** it (`precedent-checking.md`): literature precedent and funding landscape from real tool calls. Do this *before* judging novelty or risk.
3. **Count risk** (`idea-evaluation.md`): list the independent things that must go right, and the cheapest experiment that tests the shakiest one.
4. **Set the success metric and the one fixed parameter** (`idea-evaluation.md`): what result makes it worth having done, and what result means stop.
5. **Plan the decision points** (`decision-tree-navigation.md`): where will the project fork, and what evidence at each fork picks a branch. Include the fallback for each fork now, while it is cheap.
6. **Write the summary** (below).

If the user's answer at any step changes an earlier step (a precedent check shows the idea is already published; the cheapest test fails), go back to that step instead of pressing on.

## The one-page summary

Keep it to one page. Every heading must be answerable from the conversation and the tool lookups; if it is not, say what is still unknown instead of filling it in.

- **The idea in two sentences**, in the user's terms, with the kernel first.
- **Why it matters**: what changes in the field, or for patients, if it works. Say who would use the result.
- **What is already known**: 3-5 real citations (PMIDs/DOIs from the searches) and the funding picture if it was checked. State plainly if the search found the idea already done.
- **Risks**: each independent risk, how likely the user thinks it is, and the cheapest test that would settle it. Flag any risk the user has not thought about.
- **Success and stop criteria**: the result that justifies continuing and the result that ends the project.
- **The first three months**: the smallest experiment or analysis that tests the riskiest assumption, with a decision at the end of it.
- **Fallbacks**: one workaround or adjacent question that still gives a publishable or usable result if the main line fails.

## Telling it to different audiences

The same content changes emphasis, not facts:

- **Advisor or PI**: lead with the riskiest assumption and the cheap test; they will ask about it first.
- **Committee or reviewers**: lead with why it matters and what is known; show that the risk was measured, not ignored.
- **Collaborators**: lead with what each party would do and what each gets from a positive result.
- **Funders**: lead with the gap (from the funding-landscape check), the first-year deliverable, and the stop criterion.

## Checks before handing it over

- Every claim of novelty has a search behind it, and a zero-hit search was retried with at least one synonym.
- Numbers (sample sizes, effect sizes, costs, timelines) are the user's or come from a cited source; none are invented to make the plan look complete.
- The recommendation is stated as a recommendation with the one or two facts that drove it, and the user is told what would change it.
- Nothing in the summary claims the project will work. The framework lowers the chance of a bad choice; it does not predict the result.
